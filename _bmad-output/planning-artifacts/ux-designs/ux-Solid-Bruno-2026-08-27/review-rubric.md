# Spine Pair Review — Bruno Vehicle Hire

## Overall verdict

The pair is well-shaped and disciplined — section order is canonical, token cross-references resolve cleanly within DESIGN.md, and the two Key Flows that exist are excellent (named protagonist, numbered steps, real climax, failure variant). But coverage has real holes: one capability (Vehicle CRUD) and one IA surface (Customer Summary) have no Key Flow; several components in active use (form Input/Select, Top App Bar, Skeleton, Toast) have no visual or behavioral spec at all; a chunk of color tokens (the entire `text`/`text-body`/`text-muted`/`text-disabled` family, `input-border`, `surface-header`, `primary-hover`) are defined but never wired to any component or narrated use; and the `sources` frontmatter in EXPERIENCE.md has a broken relative path to `ARCHITECTURE-SPINE.md`. None of this is fatal — the spine is usable as a contract — but a story-dev consumer will hit real gaps on Vehicle screens, detail-page loading states, and generic form-field styling that this pair currently leaves to guesswork.

## 1. Flow coverage — adequate

Extracted: 2 Key Flows, both under a single memlog-confirmed "core journey" (Sipho, rental-desk agent). SPEC.md's capability list (CAP-1 through CAP-13) is the closest thing to a requirements list to check flows against.

- Flow 1 (Phone booking, then an overlap) — named protagonist (Sipho), 5 numbered steps, explicit **Climax**, explicit failure variant. Strong.
- Flow 2 (Customer asks to be forgotten) — named protagonist (Sipho), 4 numbered steps, explicit **Climax**, explicit failure variant. Strong.

### Findings
- **medium** No Key Flow exercises Vehicle management (CAP-1: create/edit/soft-delete/restore a vehicle) — the only vehicle-touching moment in either flow is checking availability by filter (EXPERIENCE.md Flow 1, step 1); creating/editing a vehicle record and the soft-delete/restore round-trip (both named IA surfaces and a named State Pattern) have no walkthrough. (EXPERIENCE.md § Key Flows). *Fix:* add a short Flow 3 (or extend Flow 1) walking a vehicle create → later soft-delete → restore.
- **low** Customer Summary (a dedicated IA surface, per EXPERIENCE.md § Information Architecture) is never reached inside a Key Flow — no flow shows an agent opening/using it during a phone call, which is the exact scenario the memlog cites as its reason for existing. (EXPERIENCE.md § Key Flows). *Fix:* fold a Customer Summary beat into Flow 1 or 2, since the phone-call framing already fits.
- **low** Neither flow cites its governing CAP-N by id (Flow 1 exercises CAP-2/3/4/5, Flow 2 exercises CAP-2/11/12), unlike the architecture-decision citations (AD-3, AD-7, AD-8, AD-13, AD-17) which are cited throughout. Makes traceability back to SPEC.md capabilities harder than it needs to be. (EXPERIENCE.md § Key Flows).

## 2. Token completeness — adequate

Extracted: 53 color tokens (incl. `-dark` pairs), 6 typography roles, 5 `rounded` scale steps, 11 `spacing` steps, 11 `components` entries in frontmatter; 47 distinct `{path.to.token}` references across DESIGN.md prose and component definitions. Every one of those 47 references resolves to a defined frontmatter token — no broken cross-references found. All color tokens that are referenced anywhere carry both a light and dark hex.

### Findings
- **high** Four base text-color token families — `text`/`text-dark`, `text-body`/`text-body-dark`, `text-muted`/`text-muted-dark`, `text-disabled`/`text-disabled-dark` (8 tokens total) — are defined in frontmatter with hex values but are **never referenced** by any `{components.*}` entry or narrated in prose anywhere in DESIGN.md. A downstream builder has no directive for which of these applies to plain body copy, muted secondary text, or disabled form text — exactly the hierarchy a dense data-table UI depends on. (DESIGN.md frontmatter `colors`, § Colors, § Typography — none mention these). *Fix:* add one sentence per token to § Colors or § Typography naming where each applies, or fold the unused ones into `{typography.body}`'s definition explicitly.
- **medium** `input-border`/`input-border-dark` and `surface-header`/`surface-header-dark` are defined but never referenced — no component uses them (there is no "Input" component in DESIGN.md.Components at all; see Component coverage). (DESIGN.md frontmatter `colors`). *Fix:* either wire them to a new Input/FilterBar-field component entry and a Top App Bar entry, or drop them.
- **medium** `primary-hover`/`primary-hover-dark` are defined but the `button-primary` component token object (frontmatter) has no `hover` field, and no prose describes a hover treatment for the primary button (or any other interactive element). (DESIGN.md frontmatter `components.button-primary`). *Fix:* add a `hover` field to `button-primary` referencing `{colors.primary-hover}`, or state the rule in § Components.
- **low** `colors.primary-foreground` has no `primary-foreground-dark` counterpart, breaking the otherwise-universal light/dark pairing convention used by every other color token. Likely intentional (white reads fine on both blues) but undocumented as a deliberate exception. (DESIGN.md frontmatter, line 34). *Fix:* one clause noting white foreground is shared across both modes by design.
- **low** `neutral-dot`/`neutral-dot-dark` and `danger-dot`/`danger-dot-dark` are defined with **identical** hex values in both light and dark variants — not wrong, but worth a one-line note that this is deliberate (small dot accents don't need mode-specific tuning) rather than a copy-paste artifact. (DESIGN.md frontmatter, lines 45-46, 51-52).
- **low** No explicit contrast ratio is stated for any specific text/background combination (EXPERIENCE.md's Accessibility Floor only asserts "designed to WCAG AA" globally). Given the tightest candidates (`text-faint`, `text-disabled` on `surface`) are exactly the tokens with no usage narrative (see above), this compounds rather than stands alone. (EXPERIENCE.md § Accessibility Floor).

## 3. Component coverage — thin

Extracted component names in use: Button (primary), Badge (+ 3 status variants), Card, DataTable, ConfirmDialog (neutral/destructive), Modal, FilterBar, error-row, Customer Summary, Skeleton (loading rows), Toast (success), Top App Bar/Nav, Input/Select (FilterBar fields, Modal form fields), Pager (pagination footer), inline booking-rule feedback / `inline-error`.

### Findings
- **critical** No **Input / form field** component exists in DESIGN.md.Components despite text inputs and selects appearing throughout FilterBar and every Create/Edit Modal — no radius, border color, focus-ring, or error-state visual spec, and no corresponding EXPERIENCE.md behavioral row. `input-border`/`input-border-dark` tokens exist but are orphaned (see Token completeness). This is the single most-used interactive element in the product and it has zero spec. (DESIGN.md § Components; EXPERIENCE.md § Component Patterns — both absent).
- **high** **Button** has a DESIGN.md.Components row (visual) but **no EXPERIENCE.md.Component Patterns row** (behavioral) — no rule for disabled-during-submit, loading spinner-in-button, or double-submit prevention on the one primary action every list/modal uses. (EXPERIENCE.md § Component Patterns).
- **high** **Toast** (used for all success confirmations, per EXPERIENCE.md § State Patterns) has no DESIGN.md visual spec (no color, position, duration, or dismiss-behavior token) and no EXPERIENCE.md Component Patterns row.
- **high** **Skeleton** (used for all list-loading states, per EXPERIENCE.md § State Patterns) has no DESIGN.md visual spec (no color/shimmer token, no row-count-per-surface guidance beyond "4-8") and no Component Patterns row.
- **medium** **Top App Bar / Nav** appears in EXPERIENCE.md's Information Architecture ("Top app bar: Bookings/Vehicles/Customers links") and in the sole mockup, and is mentioned once in passing in DESIGN.md § Colors ("active nav item") — but has no dedicated row in either DESIGN.md.Components or EXPERIENCE.md.Component Patterns (no active-state styling spec beyond the one color mention, no behavior for in-flight/unsaved-changes-on-navigate).
- **medium** **Customer Summary** has an EXPERIENCE.md.Component Patterns row (behavioral: read-only, print-friendly, no filters/row actions) but **no DESIGN.md visual counterpart** — no layout, typography, or print-specific rule despite being a distinct, purpose-built screen.
- **medium** **inline-error** (frontmatter component token: `foreground`, `fontSize`) is never referenced by `{components.inline-error}` anywhere in DESIGN.md prose, and has no dedicated row in DESIGN.md § Components — only the DataTable row's `error-row` variant is narrated. EXPERIENCE.md's "Inline booking-rule feedback" pattern (form-field-level 409/400 errors) is the token's actual use case but the two are never connected by name.
- **low** **Pager** (pagination footer — page-number links, current-page highlight, ellipsis) is used in the mockup and referenced in prose (§ Layout & Spacing, § Interaction Primitives) but has no dedicated component row in either file; likely acceptable as non-reusable page furniture rather than a true component, but worth a one-line confirmation either way.
- **low** "Dimmed row" treatment for soft-deleted vehicles (EXPERIENCE.md § State Patterns) has no stated token mapping — presumably `text-disabled`/opacity, but since that token family is orphaned (see Token completeness) the dimming rule is effectively unspecified.

## 4. State coverage — thin

Walked all 10 IA surfaces (Bookings/Vehicles/Customers list + detail + create/edit modal, Customer Summary). EXPERIENCE.md's State Patterns table covers: list loading, empty list, business-rule error, validation error (400), success, anonymized customer, soft-deleted vehicle — 7 rows.

### Findings
- **high** No loading/cold-load state is specified for any of the three **detail** surfaces (Booking detail, Vehicle detail, Customer detail) — only list loading (skeleton rows) is covered. A detail page reached by direct link/refresh needs its own loading treatment. (EXPERIENCE.md § State Patterns).
- **high** No "record not found" state anywhere (e.g., navigating to a Booking/Vehicle/Customer detail by a stale or invalid id) — not covered by any surface. (EXPERIENCE.md § State Patterns).
- **medium** No general server-error (5xx) or network-failure state is specified anywhere — only validation (400) and business-rule (409) errors are covered. Given the architecture spine's AD-8 error contract is explicitly 400/409-only at the domain level, an unhandled 500 or network drop still needs *some* UI treatment, and none is stated. (EXPERIENCE.md § State Patterns).
- **medium** No in-flight/submitting state for Create/Edit modals (e.g., primary button disabled + spinner while a POST is in flight, to prevent double-submit) — ties to the Button component-coverage gap above. (EXPERIENCE.md § State Patterns, § Component Patterns).
- **low** Customer Summary has no states of its own: no empty-bookings case ("no bookings for this customer"), no loading state, and no explicit statement of how an anonymized customer renders in this specifically-print-focused context (presumably reuses the global anonymized-customer treatment, but that's not stated for this surface). (EXPERIENCE.md § State Patterns, § Component Patterns).
- **low** Duplicate-value business rules (unique `RegistrationNumber`, unique `Email`, both 409s per ARCHITECTURE-SPINE.md AD-8) are only covered by the generic "Business-rule error" row — never named as their own case the way the booking-overlap and cancel-completed examples are. Likely fine under the generic rule but worth an explicit one-line confirmation given how specifically the booking-overlap case is treated elsewhere. (EXPERIENCE.md § State Patterns).

## 5. Visual reference coverage — thin

Files found: `mockups/bookings-list.html` (1 file — the only visual reference in the whole workspace). `wireframes/` does not exist. `imports/` exists but is empty (0 files).

### Findings
- **high** DESIGN.md never links to or mentions `mockups/bookings-list.html` anywhere — only EXPERIENCE.md does (§ Information Architecture: "Composition reference: `mockups/bookings-list.html`... Spine wins on conflict"). DESIGN.md is the file that owns every visual token the mockup exemplifies (colors, spacing, badge/table styling), so a reader validating DESIGN.md's token choices against a real rendering has no pointer to the one artifact that would let them do so. (DESIGN.md — absent throughout).
- **medium** The single mockup covers only 1 of 10 IA surfaces (Bookings list). No composition reference exists for Booking/Vehicle/Customer detail, any Create/Edit modal, or Customer Summary — all of which are named, spec'd IA surfaces with no visual anchor at all.
- **medium** The mockup itself shows a per-user identity chip ("Etienne S." avatar, top-right) — but EXPERIENCE.md's Foundation section explicitly states "no customer login... one internal staff/admin role... no permission tiers," and the architecture spine (AD-11) mandates a single shared API key with no per-user accounts. A named, avatar'd "logged-in user" contradicts the no-accounts design. "Spines win on conflict" formally resolves this, but it's a real inconsistency in the one canonical visual reference that could mislead an implementer into building per-user identity UI. (mockups/bookings-list.html, `.userchip` element vs. EXPERIENCE.md § Foundation).
- **low** "Spines win on conflict" is stated twice (EXPERIENCE.md's opening blockquote, and again in § Information Architecture) — harmless redundancy, not a defect.
- **low** The `.working/` folder holds 4 exploration renders (color-themes-1, direction-command-console, direction-ledger, direction-structured-paper) that fed the "Quiet Enterprise" decision — correctly unreferenced by either spine since they're superseded drafts, not deliverables. Noted for completeness, not a finding.

## 6. Bloat & overspecification — strong

DESIGN.md prose stays disciplined — literal px/hex values appear only alongside their token reference (matching the calibration example's style), never as unexplained magic numbers. No source material (SPEC.md capabilities, domain-model.md field lists) is restated wholesale; architecture decisions are cited by id (AD-3, AD-7, AD-8, AD-13, AD-17) rather than re-explained. Component/State Patterns use tables, not prose. The "Inspiration & Anti-patterns" section is omitted, and defensibly so on its own terms — see Shape fit for a caveat. Key Flow narrative voice (e.g., "he can read that sentence straight to the customer on the phone") matches the calibration example's own Key Flow style and isn't out of place there. No findings.

## 7. Inheritance discipline — thin

### Findings
- **critical** EXPERIENCE.md's `sources` frontmatter path to `ARCHITECTURE-SPINE.md` is **broken**: written as `'../architecture/architecture-Solid-Bruno-2026-08-25/ARCHITECTURE-SPINE.md'` (one level up), which resolves to `planning-artifacts/ux-designs/architecture/...` — a path that does not exist. The correct path from this file's location is `'../../architecture/architecture-Solid-Bruno-2026-08-25/ARCHITECTURE-SPINE.md'` (two levels up). Verified by direct filesystem resolution: the as-written path 404s, the corrected path resolves. This is the exact mechanical check the "sources frontmatter resolves" rule exists to catch — any tool or agent that programmatically follows `sources` to load the architecture spine will fail silently or error. (EXPERIENCE.md frontmatter, line 6). *Fix:* change to `'../../architecture/architecture-Solid-Bruno-2026-08-25/ARCHITECTURE-SPINE.md'`.
- **medium** Neither DESIGN.md nor EXPERIENCE.md ever cites a SPEC.md capability by its `CAP-N` id, even though EXPERIENCE.md cites architecture decisions by id (`AD-3`, `AD-7`, `AD-8`, `AD-13`, `AD-17`) extensively and consistently. Substance is correct throughout, but a downstream consumer can't grep "CAP-11" and land on the exact spine passage that implements it the way they can for AD-ids. (EXPERIENCE.md, throughout).
- **low** Key Flow 2's prose phrase "destructive-confirm-dialog treatment" (word order) doesn't byte-match the actual component/token name `confirm-dialog-destructive` (DESIGN.md frontmatter, EXPERIENCE.md's own Component Patterns table). Same referent, different string — easy to grep-miss. (EXPERIENCE.md § Key Flows, Flow 2, step 2).
- Positive note: component names are otherwise identical, byte-for-byte, across DESIGN.md.Components, DESIGN.md frontmatter `components:`, and EXPERIENCE.md.Component Patterns (`Badge`, `DataTable`, `Modal`, `FilterBar`, `ConfirmDialog (neutral)`/`(destructive)`) — strong discipline apart from Button's missing EXPERIENCE.md row (see Component coverage). The "Deactivate" relabeling of the domain's "soft-delete" term for Customer is a deliberate, uniformly-applied UX naming decision (documented in `.memlog.md`), not an inconsistency.

## 8. Shape fit — strong

DESIGN.md's 8 body sections appear in exactly the canonical order (Brand & Style → Colors → Typography → Layout & Spacing → Elevation & Depth → Shapes → Components → Do's and Don'ts), none omitted. EXPERIENCE.md's 8 required-default sections are all present (Foundation, Information Architecture, Voice and Tone, Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Key Flows). Omitting "Responsive & Platform" is correct and defensible — Foundation explicitly states this is a single-surface desktop-only app with no breakpoints to document.

### Findings
- **medium** "Inspiration & Anti-patterns" is omitted from EXPERIENCE.md, but the trigger condition for including it ("when sources / memlog show reference products or rejects") appears to be met: `.working/` contains four fully-built alternate visual directions (Quiet Enterprise, Ledger, Command Console, Structured Paper), three of which were explicitly rejected. DESIGN.md's § Shapes carries one buried sentence about this ("sharp corners were the 'Ledger'/'Command Console' register, explicitly not chosen") but the full rationale for rejecting three built-out directions in favor of Quiet Enterprise lives only in `.memlog.md`, not in either spine. (EXPERIENCE.md — section absent; DESIGN.md § Shapes — partial, one clause only). *Fix:* either add a short Inspiration & Anti-patterns section to EXPERIENCE.md summarizing the rejected directions and why, or expand DESIGN.md § Brand & Style with the same.
