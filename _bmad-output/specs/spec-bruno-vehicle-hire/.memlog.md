- (decision) Database: PostgreSQL - user's choice, open-source with no licensing overhead
- (decision) Target completion timeframe: within about 1 month, self-imposed, not externally timed by the assessment
- (capability) CAP-1 Vehicle management: intent - CRUD vehicles with soft delete; success - vehicles can be created/edited/listed/soft-deleted, and soft-deleted vehicles are excluded from booking availability and default listings
- (capability) CAP-2 Customer management: intent - CRUD customers; success - customers can be created/edited/listed, and delete is blocked with a clear error when the customer has any bookings
- (capability) CAP-3 Booking management: intent - create/view/cancel bookings linking a vehicle and customer over a date range; success - system rejects overlapping bookings per vehicle, rejects EndDate<=StartDate, blocks booking a soft-deleted vehicle, allows delete only for future bookings, and tracks status (Active/Completed/Cancelled)
- (capability) CAP-4 Search and filtering: intent - list endpoints and UI support filtering, search, and pagination across all three entities; success - filtered/paginated queries return correct subsets with correct counts
- (capability) CAP-5 Business-rule feedback UX: intent - frontend surfaces domain validation failures clearly at the point of action; success - an invalid booking attempt (e.g. overlap) shows a specific inline error, not a generic failure message
- (capability) CAP-6 Secure API access: intent - protect the API with an API key; success - requests without a valid key are rejected, and the frontend attaches the key without exposing it in source control
- (capability) CAP-7 Backend architecture demonstration: intent - implement Clean Architecture with rich domain models and CQRS; success - Domain/Application/Infrastructure/API layers are clearly separated, business rules live in domain entities and value objects, controllers stay thin, migrations are code-first (see stack.md for mandated patterns)
- (capability) CAP-8 Frontend architecture demonstration: intent - implement a scalable, feature-based Angular app; success - folder layout, module boundaries, and state-management approach match Solid-level expectations (see stack.md and architecture-diagrams.md)
- (capability) CAP-9 Automated test coverage: intent - prove core logic correctness with unit tests; success - at least 2 command tests, 2 query tests, and 1 business-rule test all pass

- (constraint) Domain business rules (no booking overlap, soft-delete exclusion, customer/booking delete guards, EndDate>StartDate) are non-negotiable - see domain-model.md; violating any is an automatic assessment failure
- (constraint) Minimum automated test coverage required: 2 command tests, 2 query tests, 1 business-rule test
